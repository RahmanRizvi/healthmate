1. EXECUTIVE SUMMARY
================================================================================
The HealthMate mobile application is a completed, fully functional, offline-first 
personal wellness tracker developed using Flutter and Dart. Its primary goal is 
to assist users in logging and tracking daily physical activity metrics (steps, 
active calories burned, and water intake), setting and customizing daily wellness 
targets, analyzing trends across Day, Week, and Month timeframes, and managing 
historical health records using a robust local SQLite database.

4. VERIFIED ARCHITECTURE AND DESIGN PATTERNS
================================================================================
4.1 Architectural Pattern Classification:
The application implements a Clean Layered Architecture with Feature-Driven 
Presentation and the MVVM (Model-View-ViewModel) Pattern.

The codebase exhibits clear separation of concerns across four distinct layers:
1. Presentation Layer (lib/presentation/):
   - Views: Pure UI widgets rendering state and capturing user input.
   - ViewModels: Extend ChangeNotifier. Maintain UI state, validate inputs, 
     invoke Domain Services, and trigger reactive UI redraws via notifyListeners().
2. Domain Layer (lib/domain/):
   - Encapsulates pure business rules and analytics in dedicated services:
     HealthRecordService, AnalyticsService, InsightsService, BmiService, OnboardingService.
   - Completely decoupled from Flutter UI widgets and database engines.
3. Data Layer (lib/data/):
   - Repository Pattern: Exposes abstract interfaces (IHealthRecordRepository, 
     IOnboardingRepository) to decouple business logic from SQLite persistence.
   - Persistence: AppDatabase encapsulates SQLite connection and CRUD queries.
   - Models: Immutable entity data classes (HealthRecord, UserProfile, DailyGoals).
4. Core Layer (lib/core/):
   - Cross-cutting constants, theme definitions, preferences, notifications, 
     and reusable widgets.

4.2 Evidence of Separation of Concerns:
- Zero SQL in UI: Across the entire lib/presentation/ directory, there are zero 
  direct database calls (no rawQuery, insert, update, or delete). All operations 
  are mediated through ViewModels and Domain Services.
- Abstract Repository Decoupling: In lib/data/repositories/health_record_repository.dart, 
  IHealthRecordRepository is defined as an abstract interface. HealthRecordService 
  depends strictly on this contract, allowing unit tests to inject in-memory 
  mock repositories without requiring a physical SQLite database.
- Centralized Dependency Injection: In lib/main.dart, MultiProvider and ProxyProvider 
  compose dependencies downward: AppDatabase -> IHealthRecordRepository -> 
  HealthRecordService -> ViewModels.

5. STATE-MANAGEMENT IMPLEMENTATION
================================================================================
5.1 State-Management Mechanism:
State management is implemented using provider: ^6.1.5+1 alongside Dart's 
built-in ChangeNotifier and Consumer pattern.

5.2 Managing Classes:
- DashboardViewModel (lib/presentation/dashboard/viewmodels/dashboard_viewmodel.dart)
- ProgressViewModel (lib/presentation/progress/viewmodels/progress_viewmodel.dart)
- RecordsViewModel (lib/presentation/records/viewmodels/records_viewmodel.dart)
- AddRecordViewModel (lib/presentation/records/viewmodels/add_record_viewmodel.dart)
- RecordDetailsViewModel (lib/presentation/records/viewmodels/record_details_viewmodel.dart)
- SettingsViewModel (lib/presentation/settings/viewmodels/settings_viewmodel.dart)
- PersonalDetailsViewModel, DailyGoalsViewModel, BmiAnalysisViewModel (Onboarding)
- ThemeController (lib/core/theme/theme_controller.dart)

5.3 UI Reactivity & Post-CRUD Refresh Strategy:
- When state mutations occur, ViewModels invoke notifyListeners().
- Subscribed views (via Consumer<T>, ChangeNotifierProvider, or context.watch<T>()) 
  rebuild their specific widget subtrees.
- Create / Update Refresh: When AddRecordScreen completes a save or update, 
  it invokes Navigator.pop(context, true). The calling screen (DashboardScreen or 
  RecordsScreen) awaits this Boolean and triggers loadDashboard() or loadRecords(), 
  re-querying SQLite and notifying listeners.
- Delete Refresh: In RecordsViewModel.deleteRecord(id), the method awaits 
  _recordService.deleteRecord(id), immediately executes await loadRecords(), and 
  calls notifyListeners(), instantly removing the item from the list.
- Quick-Add Water: In DashboardViewModel.quickAddWater(250), the method calls 
  _recordService.quickAddWaterToday(250), reloads the dashboard data, and calls 
  notifyListeners(). The circular ring and milliliters counter animate instantly.

5.4 State Representation:
- Loading: Controlled via bool _isLoading. Shows CircularProgressIndicator() or 
  disables buttons while asynchronous operations are in flight.
- Empty State: Handled cleanly when records are empty:
  * Dashboard: Shows a welcome banner for new users (isNewUser getter).
  * Records: Shows an empty-state illustration and "Add your first entry" button.
  * Progress: Shows an empty notice ("No activity logged for this period").
- Error State: Asynchronous operations are wrapped in try-catch blocks. Errors 
  are captured in String? _errorMessage and displayed via Snackbars or inline labels.

8. CRUD IMPLEMENTATION (CREATE, READ, UPDATE, DELETE)
================================================================================

All four CRUD operations are fully implemented and verified:

8.1 CREATE
- UI Screen       : AddRecordScreen (lib/presentation/records/views/add_record_screen.dart)
- ViewModel       : AddRecordViewModel (lib/presentation/records/viewmodels/add_record_viewmodel.dart)
- Validation      : validate() ensures steps, calories, and water are integers >= 0 
                    and selected date is not in the future.
- Service Method  : HealthRecordService.saveRecord(record)
- Repository Method: HealthRecordRepository.saveRecord(record)
- SQLite Method   : AppDatabase.saveHealthRecord(record) -> db.insert('health_records', 
                    record.toMap(), conflictAlgorithm: ConflictAlgorithm.replace)
- UI Response     : Shows confirmation snackbar, pops route returning true, 
                    triggering parent dashboard or records reload.

8.2 READ
- Today's Summary : HealthRecordService.getTodayRecord() -> AppDatabase.getHealthRecordByDate()
- All Records List: RecordsViewModel.loadRecords() -> HealthRecordService.getAllRecords() 
                    -> AppDatabase.getAllHealthRecords() -> db.query('health_records', orderBy: 'date DESC')
- Range Query     : AnalyticsService.getAnalyticsForPeriod() -> AppDatabase.getHealthRecordsForDateRange()
- Deserialization : HealthRecord.fromMap(map) transforms rows into Dart objects.

8.3 UPDATE
- UI Screen       : AddRecordScreen in edit mode, passing existingRecord.
- Form Population : AddRecordViewModel.initWithRecord(record) pre-populates 
                    controllers and steppers with existing metrics.
- Service Method  : HealthRecordService.updateRecord(record)
- Repository Method: HealthRecordRepository.updateRecord(record)
- SQLite Method   : AppDatabase.updateHealthRecord(record) -> db.update('health_records', 
                    record.toMap(), where: 'id = ?', whereArgs: [record.id])
- UI Response     : Pops route returning true, triggering parent re-query and redrawing.

8.4 DELETE
- UI Trigger      : Trash icon in RecordsScreen or RecordDetailsScreen.
- Confirmation    : ConfirmationDialog prompts user with destructive warning.
- ViewModel Method: RecordsViewModel.deleteRecord(id)
- Service Method  : HealthRecordService.deleteRecord(id)
- Repository Method: HealthRecordRepository.deleteRecord(id)
- SQLite Method   : AppDatabase.deleteHealthRecord(id) -> db.delete('health_records', 
                    where: 'id = ?', whereArgs: [id])
- UI Response     : Awaits deletion, immediately calls await loadRecords(), and 
                    invokes notifyListeners(), animating item removal from UI.

9. SEARCH, FILTERING, AND DASHBOARD LOGIC
================================================================================
9.1 Search Implementation:
Implemented in RecordsViewModel.filteredRecords (lib/presentation/records/viewmodels/records_viewmodel.dart:L104-L130).
Performs case-insensitive dynamic matching across:
- ISO date strings (e.g., "2026-10-21")
- Full formatted dates (e.g., "21 October 2026")
- Abbreviated dates (e.g., "Oct 21", "21 Oct")
- Month names (e.g., "October")
- Weekday names (e.g., "Wednesday")
- Exact calendar day or year numbers

9.2 Date Filtering Implementation:
Controlled by DateFilterType in RecordsViewModel:
- All         : Displays all records in SQLite.
- Today       : Filters for records matching DateFormatter.toIsoDateString(DateTime.now()).
- This Week   : Filters records between Monday and Sunday of the current week.
- This Month  : Filters records matching current year and month.
- Custom Range: Filters records within user-selected DateTimeRange or specific date.

9.3 Dashboard Calculations (Verified Real Data):
The dashboard displays 100% REAL stored SQLite data. It contains NO hardcoded values:
- Today's Metrics : Read from _todayRecord. If no entry exists for today, displays 0.
- Activity Rings  : Normalized ratio calculated as (todayValue / goalValue).clamp(0.0, 1.0).
- 7-Day Chart     : HealthRecordService.getWeeklyActivityData() fetches Monday-Sunday 
                    records from SQLite, calculates normalized heights, and averages 
                    steps across recorded days.
- Consecutive Streak: HealthRecordService.calculateDailyStreak() gathers all active 
                    dates into a Set<String> and loops backward from today/yesterday.
