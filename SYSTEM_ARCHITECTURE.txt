1. HIGH-LEVEL ARCHITECTURE OVERVIEW
================================================================================
HealthMate is built following Clean Layered Architecture and the MVVM (Model-
View-ViewModel) design pattern. The codebase separates user interface, business 
rules, data access, and core infrastructure into distinct, decoupled layers:

 [ Presentation Layer (UI & ViewModels) ]
                    |
                    v (calls domain services via Dependency Injection)
 [ Domain Layer (Business Services & Calculations) ]
                    |
                    v (depends on abstract repository interfaces)
 [ Data Layer (Repositories, Models, SQLite Database) ]
                    ^
                    | (shared cross-cutting utilities, theme & preferences)
 [ Core Layer (Constants, Utilities, Theming, Preferences) ]

Key architectural qualities:
- Complete offline-first capability via SQLite (`sqflite`).
- Reactive UI state updates via `provider` (`ChangeNotifierProvider`, `Consumer`).
- Decoupled contracts via abstract repository interfaces (`IHealthRecordRepository`, 
  `IOnboardingRepository`), enabling fast, deterministic unit and widget testing 
  without physical SQLite dependencies.
- Strict null safety and robust validation across models and UI input fields.

3. LAYER-BY-LAYER COMPONENT RESPONSIBILITIES
================================================================================

--------------------------------------------------------------------------------
3.1 PRESENTATION LAYER
--------------------------------------------------------------------------------
The presentation layer is responsible exclusively for UI rendering, user input 
capture, animations, and binding to ViewModels. It contains NO SQL or direct 
storage operations.

A. Views (Screens):
- SplashScreen (`lib/presentation/splash/views/splash_screen.dart`):
  Checks onboarding completion via `OnboardingService`. Seamlessly directs 
  new users to `WelcomeScreen` and existing users to `DashboardScreen`.
- WelcomeScreen (`lib/presentation/onboarding/views/welcome_screen.dart`):
  Initial introduction screen detailing app value propositions.
- PersonalDetailsScreen (`lib/presentation/onboarding/views/personal_details_screen.dart`):
  Captures name, date of birth, gender, height, and weight with live form validation.
- BmiAnalysisScreen (`lib/presentation/onboarding/views/bmi_analysis_screen.dart`):
  Displays computed BMI score, WHO category (Underweight, Normal, Overweight, Obese),
  and personalized health guidance before proceeding.
- DailyGoalsScreen (`lib/presentation/onboarding/views/daily_goals_screen.dart`):
  Allows user to set custom or recommended daily goals for steps, water, and calories.
- DashboardScreen (`lib/presentation/dashboard/views/dashboard_screen.dart`):
  Central hub displaying:
  * Personalized greeting and current date
  * Consecutive daily logging streak badge
  * 3 Activity Progress Cards (Steps, Calories, Water with quick +250ml action)
  * 7-day Weekly Activity bar chart
  * Recent activity records list
- ProgressScreen (`lib/presentation/progress/views/progress_screen.dart`):
  Analytics powerhouse with:
  * Day / Week / Month period selector with calendar date range badge
  * Interactive Steps Bar Chart (tap any bar to inspect metrics)
  * Hydration Trend Line Chart
  * Dynamic Wellness Insight Card & Rotating Tips
  * Daily Goal Completion Progress Bars (% of target reached)
  * CSV export modal dialog
- RecordsScreen (`lib/presentation/records/views/records_screen.dart`):
  Historical logs viewer with:
  * Summary Cards (total records, average steps, total water)
  * Instant search bar (searches by date, month name, weekday, year)
  * Date filter chips (All, Today, This Week, This Month, Custom Date Range)
  * Sort order toggle (Newest First <-> Oldest First)
  * Swipe-to-delete or tap-to-delete with confirmation dialog
- AddRecordScreen (`lib/presentation/records/views/add_record_screen.dart`):
  Modal form to log or edit activity for any calendar date (past or present).
- RecordDetailsScreen (`lib/presentation/records/views/record_details_screen.dart`):
  Full-screen inspection of a single day's record with breakdown and goal badges.
- Settings Screens (`lib/presentation/settings/views/*`):
  Manages user profile editing, goal modifications, theme toggling (Light/Dark/System),
  unit toggling (Metric/Imperial), notification scheduling, privacy, and terms.

B. ViewModels:
- DashboardViewModel: Manages dashboard state, refreshes on resume, quick-adds water.
- ProgressViewModel: Handles date range navigation, chart point selection, CSV generation.
- RecordsViewModel: Implements debounced search, date filtering, sorting, and deletion.
- AddRecordViewModel: Validates form fields (steps, kcal, ml), ensures date uniqueness.
- RecordDetailsViewModel: Loads single record, computes percentages against user goals.
- SettingsViewModel: Coordinates theme switching, notification permission requests, units.
- Onboarding ViewModels (`PersonalDetailsViewModel`, `DailyGoalsViewModel`, etc.):
  Manage state step-by-step through the multi-page registration funnel.

C. Feature Widgets:
- Dedicated charts (`StepsActivityChart`, `HydrationTrendChart`, `WeeklyActivityChart`)
- Navigation (`BottomNavigation` with 4 main tabs)
- Dialogs (`ProgressExportDialog`, `ConfirmationDialog`)

--------------------------------------------------------------------------------
3.2 DOMAIN LAYER
--------------------------------------------------------------------------------
The domain layer encapsulates pure business logic, calculations, and rules. It 
is decoupled from Flutter UI widgets and database drivers.

- HealthRecordService (`lib/domain/services/health_record_service.dart`):
  * Coordinates CRUD operations through `IHealthRecordRepository`.
  * Computes 7-day weekly activity points (`WeeklyDayPoint`, `WeeklyActivityData`).
  * Calculates active daily logging streaks across calendar dates.
  * Evaluates goal achievement status: `RecordGoalStatus.goalMet`, `partial`, `none`.
  * Computes overall percentage completion across steps, calories, and water.
- AnalyticsService (`lib/domain/services/analytics_service.dart`):
  * Generates calendar-accurate `PeriodDayPoint` collections for Day/Week/Month.
  * Calculates summary statistics (total steps, averages, total water litres).
  * Computes goal achievement frequency (% of elapsed days targets were met).
  * Evaluates period-over-period comparisons (e.g., +15% vs last week).
  * Identifies best and lowest recorded days in any time window.
- InsightsService (`lib/domain/services/insights_service.dart`):
  * Analyzes data points to generate actionable natural-language feedback.
  * Produces contextual categories: `streak`, `achievement`, `hydration`, `improvement`.
- BmiService (`lib/domain/services/bmi_service.dart`):
  * Takes `UserProfile` and delegates to `BmiCalculator` for WHO categorization.
  * Returns healthy weight ranges and clinical advice.
- OnboardingService (`lib/domain/services/onboarding_service.dart`):
  * Coordinates user registration, profile retrieval, and onboarding verification.

--------------------------------------------------------------------------------
3.3 DATA LAYER
--------------------------------------------------------------------------------
The data layer is responsible for persistence, serialization, and interaction 
with the SQLite database engine.

- AppDatabase (`lib/data/database/app_database.dart`):
  * Manages SQLite connection lifecycle, database versioning, and migrations.
  * Tables:
    1. `user_profile`: id, full_name, date_of_birth, gender, height_cm, weight_kg, timestamps
    2. `daily_goals`: id, steps_goal, water_goal_ml, calories_goal_kcal, updated_at
    3. `health_records`: id, date (UNIQUE `yyyy-MM-dd`), steps, calories, water, timestamps
  * Implements atomic transactions (e.g., `incrementWaterForDate`).
  * Employs `ConflictAlgorithm.replace` to prevent duplicate entries on the same date.
- Repositories:
  * `IHealthRecordRepository` & `HealthRecordRepository`:
    Abstracts record querying by ID, date, date range, or all records.
  * `IOnboardingRepository` & `OnboardingRepository`:
    Abstracts user profile and daily goal persistence.
- Models (Data Entities):
  * `HealthRecord`: Immutable data class representing a daily log.
  * `UserProfile`: Immutable data class representing user demographics.
  * `DailyGoals`: Immutable data class representing daily targets.
  All models feature `toMap()`, `fromMap()`, `copyWith()`, `operator ==`, and `hashCode`.

--------------------------------------------------------------------------------
3.4 CORE LAYER
--------------------------------------------------------------------------------
Provides fundamental utilities, design constants, and system wrappers across 
all layers.

- Constants:
  * `AppColors`: Primary emerald green (`#00A86B`), dark/light cards, text colors.
  * `AppDimensions`: Standardized margins, paddings, border radiuses, icon sizes.
- Theme:
  * `AppTheme`: Full Material 3 theme configurations for light and dark modes.
  * `ThemeController`: Manages runtime switching between System, Light, and Dark.
- Preferences:
  * `AppPreferences`: SharedPreferences wrapper for unit settings and reminders.
- Notifications:
  * `NotificationService`: Manages local OS alerts for daily reminders and weekly digests.
- Utilities:
  * `AgeCalculator`: Computes age accurately considering leap years and birth month.
  * `BmiCalculator`: Calculates BMI = weight (kg) / (height (m))^2 and category.
  * `DateFormatter`: Formats ISO dates (`yyyy-MM-dd`), greetings, and badges.
  * `DateRangeUtils`: Calendar math to calculate Day, Week, and Month boundaries.
  * `UnitConverter`: Converts between cm <-> ft/in and kg <-> lbs.
- Core Widgets:
  * Reusable buttons, text fields, headers, cards, and bottom navigation.

4. OBJECT-ORIENTED PROGRAMMING (OOP) IMPLEMENTATION MAPPING
================================================================================

HealthMate heavily utilizes core Object-Oriented Programming (OOP) principles 
to produce clean, maintainable, extensible, and testable code.

--------------------------------------------------------------------------------
4.1 ABSTRACTION
--------------------------------------------------------------------------------
Abstraction hides internal implementation complexities and exposes only clean, 
well-defined interfaces.

Examples in HealthMate:
1. Abstract Repository Interfaces:
   File: `lib/data/repositories/health_record_repository.dart`
   ```dart
   abstract class IHealthRecordRepository {
     Future<HealthRecord?> getRecordById(int id);
     Future<HealthRecord?> getRecordByDate(String date);
     Future<List<HealthRecord>> getAllRecords();
     Future<List<HealthRecord>> getRecordsForDateRange(String startDate, String endDate);
     Future<int> saveRecord(HealthRecord record);
     Future<int> updateRecord(HealthRecord record);
     Future<int> deleteRecord(int id);
     Future<void> incrementWater(String date, int amountMl);
   }
   ```
   The `HealthRecordService` only knows about `IHealthRecordRepository`. It has 
   zero knowledge of SQLite, SQL queries, or tables. This allows substituting 
   an in-memory mock repository during unit tests.

2. Onboarding Repository Interface:
   File: `lib/data/repositories/onboarding_repository.dart`
   ```dart
   abstract class IOnboardingRepository {
     Future<UserProfile?> getUserProfile();
     Future<void> saveUserProfile(UserProfile profile);
     Future<DailyGoals?> getDailyGoals();
     Future<void> saveDailyGoals(DailyGoals goals);
     Future<bool> isOnboardingCompleted();
   }
   ```

3. ChangeNotifier Abstraction:
   ViewModels inherit from Flutter's abstract `ChangeNotifier`, abstracting the 
   Observer pattern so that views only listen to notifications rather than 
   manually coordinating redraws.

--------------------------------------------------------------------------------
4.2 ENCAPSULATION
--------------------------------------------------------------------------------
Encapsulation bundles data with the methods that operate on that data and restricts 
direct access to internal mutable state using access modifiers (private variables 
prefixed with `_`).

Examples in HealthMate:
1. Encapsulated State in ViewModels:
   File: `lib/presentation/dashboard/viewmodels/dashboard_viewmodel.dart`
   ```dart
   class DashboardViewModel extends ChangeNotifier {
     final OnboardingService _onboardingService;
     final HealthRecordService _recordService;

     UserProfile? _profile;
     DailyGoals? _goals;
     HealthRecord? _todayRecord;
     bool _isLoading = true;

     // Controlled public read-only accessors:
     UserProfile? get profile => _profile;
     DailyGoals? get goals => _goals;
     HealthRecord? get todayRecord => _todayRecord;
     bool get isLoading => _isLoading;
   }
   ```
   External widgets cannot directly mutate `_isLoading` or `_todayRecord`. State 
   transitions must pass through explicit methods like `loadDashboard()` or 
   `quickAddWater()`.

2. Private Database Singleton Constructor:
   File: `lib/data/database/app_database.dart`
   ```dart
   class AppDatabase {
     static final AppDatabase _instance = AppDatabase._internal();
     factory AppDatabase() => _instance;
     AppDatabase._internal(); // Private constructor prevents external instantiation
     Database? _database;     // Private connection instance
   }
   ```

3. Immutable Entities with Defensive Copies:
   File: `lib/data/models/health_record.dart`
   All fields are `final`. Object modification requires `copyWith()`, ensuring 
   unintended mutations cannot happen anywhere in the system.

--------------------------------------------------------------------------------
4.3 INHERITANCE
--------------------------------------------------------------------------------
Inheritance allows classes to derive properties and behavior from superclasses, 
fostering code reuse.

Examples in HealthMate:
1. ViewModels Extending `ChangeNotifier`:
   ```dart
   class RecordsViewModel extends ChangeNotifier { ... }
   class ProgressViewModel extends ChangeNotifier { ... }
   class ThemeController extends ChangeNotifier { ... }
   ```
   Inherits `addListener()`, `removeListener()`, and `notifyListeners()` from 
   the Flutter SDK foundation.

2. Widgets Extending `StatelessWidget` and `StatefulWidget`:
   All UI components (`DashboardScreen`, `ProgressScreen`, `PrimaryButton`, etc.) 
   inherit from Flutter's core widget hierarchy, participating in the widget 
   lifecycle and layout system.

--------------------------------------------------------------------------------
4.4 POLYMORPHISM
--------------------------------------------------------------------------------
Polymorphism allows different classes to be treated through a common interface, 
with each class executing its own specific implementation.

Examples in HealthMate:
1. Interface Implementation Polymorphism:
   ```dart
   class HealthRecordRepository implements IHealthRecordRepository { ... }
   class MockHealthRecordRepository implements IHealthRecordRepository { ... }
   ```
   Both classes implement `IHealthRecordRepository`. In production, `main.dart` 
   injects `HealthRecordRepository`. In unit tests (`health_record_service_test.dart`), 
   a mock repository is passed to the same service constructor without changing 
   a single line of domain logic.

2. Method Overriding (`@override`):
   - Overriding `Widget build(BuildContext context)` across all widgets.
   - Overriding `operator ==` and `hashCode` in `HealthRecord`, `UserProfile`, 
     and `DailyGoals` to achieve value-based object comparison rather than 
     memory reference comparison.

--------------------------------------------------------------------------------
4.5 COMPOSITION OVER INHERITANCE
--------------------------------------------------------------------------------
HealthMate strictly adheres to "Composition over Inheritance":
1. Service & ViewModel Composition:
   `DashboardViewModel` is NOT an extension of `HealthRecordService`. Instead, 
   it COMPOSEs instances of `OnboardingService` and `HealthRecordService`.
2. Flutter Widget Trees:
   Screens are composed of smaller reusable widgets (`ActivityProgressCard`, 
   `WeeklyActivityChart`, `RecordHistoryCard`) rather than deep inheritance chains.
3. ProxyProvider Pipeline:
   `MultiProvider` composes dependencies by injecting `AppDatabase` into 
   `HealthRecordRepository`, which is then composed into `HealthRecordService`, 
   which is then composed into `DashboardViewModel`.


================================================================================
5. DESIGN PATTERNS & ARCHITECTURAL PARADIGMS ("AND OTHER")
================================================================================

--------------------------------------------------------------------------------
5.1 MVVM (MODEL-VIEW-VIEWMODEL) PATTERN
--------------------------------------------------------------------------------
- Model:
  Data classes (`HealthRecord`, `DailyGoals`, `UserProfile`) and business services.
- View:
  Flutter Widgets (`DashboardScreen`, `RecordsScreen`, etc.) that render pixels 
  and emit user events (button taps, text input).
- ViewModel:
  `DashboardViewModel`, `RecordsViewModel`, `ProgressViewModel`. Maintains UI 
  state, validates user input, coordinates with domain services, and notifies 
  the View when state changes.

--------------------------------------------------------------------------------
5.2 REPOSITORY PATTERN
--------------------------------------------------------------------------------
Decouples domain business logic from the underlying storage mechanism (SQLite). 
If the storage is migrated in the future (e.g., from SQLite to REST API or Hive), 
only the repository implementation changes; domain services and UI remain 
untouched.

--------------------------------------------------------------------------------
5.3 DEPENDENCY INJECTION (DI) & INVERSION OF CONTROL (IoC)
--------------------------------------------------------------------------------
Configured in `lib/main.dart` via `MultiProvider` and `ProxyProvider`:
```dart
MultiProvider(
  providers: [
    Provider<AppDatabase>(create: (_) => AppDatabase()),
    ProxyProvider<AppDatabase, IHealthRecordRepository>(
      update: (_, db, __) => HealthRecordRepository(db: db),
    ),
    ProxyProvider<IHealthRecordRepository, HealthRecordService>(
      update: (_, repo, __) => HealthRecordService(repository: repo),
    ),
    ...
  ],
  child: ...,
)
```
Dependencies flow downward. High-level modules do not depend on low-level 
modules; both depend on abstractions.

--------------------------------------------------------------------------------
5.4 OBSERVER PATTERN
--------------------------------------------------------------------------------
Implemented using `ChangeNotifier` and Flutter's `Consumer` / `ListenableBuilder`:
1. User taps "+250ml Water" on the dashboard.
2. `DashboardViewModel.quickAddWater(250)` is invoked.
3. The ViewModel updates SQLite and calls `notifyListeners()`.
4. All listening `Consumer<DashboardViewModel>` widgets automatically re-render 
   the updated water progress ring and milliliters label.

--------------------------------------------------------------------------------
5.5 SINGLETON PATTERN
--------------------------------------------------------------------------------
Used for system-wide single-point resources:
- `AppDatabase`: Ensures only one active SQLite connection pool exists.
- `NotificationService`: Manages a single notification plugin instance across the OS.
- `AppPreferences`: Single access point for cached device preferences.

--------------------------------------------------------------------------------
5.6 FACTORY METHOD PATTERN
--------------------------------------------------------------------------------
Extensively utilized for object instantiation:
- `HealthRecord.fromMap(Map<String, dynamic> map)`: Deserializes database rows.
- `HealthRecord.empty(DateTime dateTime)`: Creates a zeroed default daily entry.
- `DailyGoals.defaults()`: Creates recommended health goals.
- `BmiResult.empty()`: Fallback null-object representation for uninitialized BMI.

--------------------------------------------------------------------------------
5.7 VALUE OBJECT PATTERN & IMMUTABILITY
--------------------------------------------------------------------------------
Models represent immutable Value Objects. Two `HealthRecord` instances with the 
exact same date, steps, calories, and water evaluate as equal (`==`), preventing 
erroneous duplicates and side-effects.

--------------------------------------------------------------------------------
5.8 STRATEGY / PURE CALCULATION SERVICES
--------------------------------------------------------------------------------
Complex algorithms are decoupled into pure stateless calculation utilities:
- `BmiCalculator`: WHO formula calculation and threshold matching.
- `DateRangeUtils`: Boundary calculations for Day, Week, and Month navigation.
- `AgeCalculator`: Real-world calendar age determination.
- `UnitConverter`: Bidirectional unit conversion formulas.


================================================================================
6. COMPLETE END-TO-END DATA FLOW PIPELINE
================================================================================

Example: User logs a new health entry in AddRecordScreen.

Step 1: User Interaction (UI)
User enters 8,500 steps, 420 kcal, 2,000 ml water on `AddRecordScreen` and taps 
"Save Record".

Step 2: Validation (ViewModel)
`AddRecordViewModel.saveRecord()` executes:
- Validates that values are positive integers.
- Constructs an immutable `HealthRecord` object.

Step 3: Business Logic (Domain Service)
ViewModel calls `HealthRecordService.saveRecord(record)`:
- Evaluates goal achievement status.
- Updates streak calculations if necessary.

Step 4: Persistence (Data Repository)
Service calls `IHealthRecordRepository.saveRecord(record)`.

Step 5: Database Execution (SQLite)
`HealthRecordRepository` invokes `AppDatabase.saveHealthRecord(record)`:
- Executes `db.insert('health_records', ..., conflictAlgorithm: replace)`.
- Record is committed to the local SQLite database file.

Step 6: Reactive UI Propagation
- Screen pops with `Navigator.pop(context, true)`.
- Parent `RecordsViewModel` or `DashboardViewModel` invokes `loadRecords()` 
  or `loadDashboard()`.
- ViewModel re-queries SQLite, updates internal state, and calls `notifyListeners()`.
- `DashboardScreen` and `ProgressScreen` redraw with new percentages, charts, 
  and streak count.
